# Wallpaper Engine 容器格式速查

官方没有任何文档。下面每个字段都是拿真实文件反推、并用**"总长度必须严丝合缝"自校验**过的。

实测样本：`3212720589`（PKGV0020 / TEXB0003）与 `3660962877`（PKGV0023 / TEXB0004），
2026-10-02 逆向完成。

## 1. `scene.pkg` — PKGV0020 / PKGV0023

```
[uint32 magic_len = 8]
[char   magic[8] = "PKGV0020"（新的是 "PKGV0023"）]
[uint32 条目数 = N]
重复 N 次:
    [uint32 路径长度 L]
    [char   路径[L]]        UTF-8，形如 shaders/effects/tint.vert、materials/xxx.tex
    [uint32 偏移 offset]     ← 相对"数据区起点"，不是文件开头
    [uint32 长度 size]
[数据区]                     ← 紧跟条目表，无对齐填充
```

**自校验**：`sum(size) + 条目表长度 == 文件长度`。
0020 样本 42 条、0023 样本 68 条，两者差值都是 0。

`PKGV0001` / `PKGV0002` 没样本，未验证。

## 2. `.tex` — TEXV0005

```
"TEXV0005\0"                      9 字节，含结尾 NUL
"TEXI0001\0"                      9 字节
[i32 格式]       ← 贴图格式码，见 §2.3
[i32 标志]
[i32 宽][i32 高]
[i32 宽2][i32 高2]
[i32 未知]

"TEXB0003\0"  或  "TEXB0004\0"    9 字节 —— **两者布局差一个 i32，见下**
[i32 图像数]
  每张图:
    [i32 图像格式]     -1 = 继承头部那个；实测 13 = 该 mip 存的是 PNG
    ★ TEXB0004 比 0003 在这里**多一个 i32**（实测恒为 0，直接跳过）
    [i32 mip 数]
      每个 mip:
        [i32 宽][i32 高]
        [i32 压缩]        0 = 原样（数据区是完整文件）；1 = LZ4 块压缩
        [i32 解压后大小]     RGBA 时 = 宽×高×4；存完整文件时为 0
        [i32 数据长度]
        [数据]             ← 没有对齐填充
```

样本自校验：`3840×2160 fmt=0 未压缩=0 数据长=40125357 数据@87`，
`87 + 40125357 = 40125444 = 文件长度` —— 差 0。

### 2.1 「贴图」其实是完整文件（视频 / PNG）

`压缩 == 0` 时，数据区**不是裸像素，而是一个完整文件**，靠 magic 认：

| 开头 | 是什么 |
|---|---|
| `00 00 00 18 66 74 79 70` | **MP4**（box 长 24 + `ftyp`）—— 4K 动态壁纸的正片 |
| `89 50 4E 47 0D 0A 1A 0A` | **PNG**（带 alpha 的贴图 WE 会直接存 PNG，每个 mip 一张） |

实测正片：`ftyp mp42 → moov → uuid → free → mdat`，**h264 3840×2160 60fps 20.01s + aac**；
另一例 `4000×2300 60fps 34.6 Mbps`。**`moov` 在前（faststart），改后缀直接能播，无需转码。**

### 2.2 mip 数据是**裸 LZ4 块**

`压缩 == 1` 的 mip 是**没有帧头的 LZ4 block**（不是 LZ4 frame，别找魔数）。
解压后长度必须**正好等于**头里的"解压后大小"。实测压缩比 2.5~250:1（大面积纯色的蒙版最高）。

`we_extract.py` 里的 `lz4_raw()` 就是为此写的，约 30 行。

### 2.3 贴图格式码 —— 网上流传的对照表是错的

| 码 | 实测含义 | 状态 |
|---|---|---|
| 0 | RGBA8888（4 B/px） | **已坐实**（`unc == 宽×高×4`） |
| 4 | **DXT5 / BC3**（16 B / 4×4 块 = 1 B/px） | **已坐实**（解出来是完美图像） |
| 9 | **R8 灰度**（1 B/px） | **已坐实**（解出来是圆角蒙版） |
| 其它 | 按 `解压后大小 / (宽×高)` 推断 | 推断，脚本会标注 |

> 网上那张表（0=RGBA、1=DXT5、2=DXT3、3=DXT1、**4=RG88**、5=R8）**和实测对不上**：
> 格式码 4 的 832×832 贴图，按 RG88 解需要 1 384 448 B，但 `unc` 只有 692 224 B；
> 按 DXT5 解出来是一只完整的 Q 版角色立绘。**所以一律以数据长度自校验为准，不迷信对照表。**
>
> DXT3 与 DXT5 同长（16 B/块），纯靠长度分不开 —— 所以脚本只在"尺寸验证通过"时才敢解，
> 且**只认已坐实的那几个码**，未知码宁可按每像素字节数推断并标注，也不硬套。

### 2.4 一个曾经的"反例"

早期记过一例：某 `500x500.tex` 声明 `fmt=0`（RGBA8888）但只有 3935 字节，
而 500×500×4 要 1 000 000 字节，当时判为"长度对不上任何已知格式"。
**答案：它的 `压缩 == 1`，是 LZ4 块。**解压后正好 1 000 000 字节，出图正常。
**任何"长度对不上"的情况，先检查 `压缩` 字段，再怀疑格式码。**

## 3. 实现说明

`we_extract.py` 自带 BC1/BC2/BC3 解码（`decode_bc()`）和 PNG 写出（`write_png()`，
用标准库 `zlib`），**整条链路零第三方依赖**。

早先那版"套 128 字节 DDS 头交给 Pillow 的 `DdsImagePlugin`"的做法已废弃：
Pillow 对 `mipMapCount` / `pitchOrLinearSize` 挑剔，遇到本样本会报
`image file is truncated (12 bytes not processed)`。

跑 `python3 selftest.py` 可以不需要任何真实壁纸就验证上述全部结论。
